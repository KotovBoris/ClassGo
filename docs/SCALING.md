# Масштабирование и тиражирование «ClassGo»

Критерий «Потенциал масштабирования» весит **35%** продуктовой оценки онлайн-этапа и **25%**
финала. Документ отвечает на требования критерия по пунктам.

---

## 1. Ядро продукта (не меняется при масштабировании)

Это то, что переносится в новый контекст **без изменений кода**:

| Элемент ядра | Почему устойчив |
|---|---|
| Ответ родителя по ученику | завязан на ребёнка, а не на школу или регион |
| Модель «Организатор — Группа — Участник — Родитель» | не содержит гео- или ведомственных сущностей |
| Механика сводки ответов и напоминаний | зависит только от статусов согласие/билет |
| Генератор нормативных документов | шаблон приказа параметризован (школа, маршрут, участники) |
| Архитектура (FastAPI + MAX-адаптер + mini-app) | MAX — единственный канал, он федеральный |
| Модель данных (код ORM) | доступ через SQLModel/SQLAlchemy — **не зависит от конкретной СУБД** |
| Базовые элементы интерфейса | каталог, дашборд, экран родителя |

## 2. Переменная часть (что адаптируется под контекст)

| Что меняется | Как |
|---|---|
| Данные о событиях | подключение фида региона: PRO.Культура.РФ / Culture.РФ / региональный портал |
| Справочник площадок и адресов | нормализация по ФИАС (единый ГАР-классификатор) |
| Билетные операторы | список доменов-шлюзов для ссылок на оплату |
| Правила выезда | локальные регламенты школы/региона (шаблон приказа) |
| Роли и модераторы | добавление роли администрации, региональных кураторов |
| Язык интерфейса | татарский/другие языки регионов (i18n) |
| **СУБД** | SQLite в демо → PostgreSQL в проде при росте: **нагрузка, несколько инстансов**. Переключение — переменная `DATABASE_URL` (проверено 189 тестами на обеих БД) |

### Отдельно про базу данных

Разделяем две разные роли БД, чтобы это было честно и проверяемо:

- **Данные каталога** (события, площадки) — точно **переменная часть**: регион подключает свой фид.
- **Схема данных и код доступа** (модель «класс → ученики → родители», согласия, аудит) — **ядро**:
  доступ идёт через ORM (SQLModel/SQLAlchemy) и **не зависит от конкретной СУБД**, поэтому смена
  SQLite → PostgreSQL не меняет ни логику, ни модель, только строку подключения.
- **Тип СУБД** — параметр развёртывания, а не часть ядра. SQLite выбран для пилота (ноль настройки,
  ноль накладных расходов), PostgreSQL — для продакшена при масштабировании (параллельная запись,
  несколько инстансов сервиса, аналитика уровня департамента).

## 3. Конкретные контексты тиражирования (по убыванию близости)

1. **Общее образование (исходный кейс).** Классные руководители → школы → департаменты
   образования городов. Следующий шаг: пилот в Казани (Департамент образования).
2. **Вузы и колледжи.** Выездные практики, студвесна, волонтёрские акции: та же связка
   «группа — участник — согласие — документы», меняется только шаблон.
3. **Спортивные школы и секции (ДЮСШ).** Согласия на выездные соревнования и сборы,
   список тренеров-сопровождающих вместо учителей.
4. **Детские лагеря и допобразование.** Согласование экскурсионных дней внутри смены.
5. **Муниципальный/региональный уровень.** Единая панель для департамента: агрегированная
   статистика по выездам школ (в исходном кейсе — п.7 PRD).

## 4. Порядок тиражирования (реалистичный путь)

```
Пилот в 1 школе (3–5 классов, 1 четверть)
      │ метрики: 100% выездов через сервис, сбор ≤ 24 ч, 0 потерянных согласий
      ▼
3–5 школ города (подключение регионального фида событий + справочника площадок)
      ▼
Уровень департамента образования города (единая панель, роли кураторов)
      ▼
Новый регион (тираж ядра + локальный фид данных и справочник)
      ▼
Вертикали: вузы / ДЮСШ / лагеря (смена шаблонов документов)
```

## 5. Что потребуется на каждом шаге

| Шаг | Данные | Интеграции | Ресурсы / участники |
|---|---|---|---|
| Пилот в школе | демо-данные заменяются реальным списком класса | MAX Bot API | 1 учитель-энтузиаст, родители |
| Уровень города | региональный фид событий | API PRO.Культура.РФ, кассы музеев | методист, ИТ-поддержка школы |
| Уровень департамента | агрегаты по школам | SSO/ЕСИА, оргструктура | департамент, DPO школы |
| Новый регион | фид региона, ФИАС | локальные порталы культуры | региональный оператор |
| Вертикали (вузы/ДЮСШ) | шаблоны документов | те же | профильные ведомства |

## 6. Ключевые риски масштабирования и их снижение

| Риск | Снижение |
|---|---|
| Юридическая типовка приказа различается по регионам | шаблон выносится в конфиг; выверка юристом школы |
| ПДн детей | согласие на обработку, шифрование, минимизация данных |
| Доступность внешних API (PRO.Культура.РФ) | кэш/снапшот каталога + асинхронная синхронизация |
| Нагрузка на кассу музея при массовых выездах | переход на билетные API операторов, квоты |
| Зависимость от одной платформы (MAX) | архитектура ports&adapters: домен не завязан на MAX |

## 7. Почему это не «мы запустимся в Москве и Питере»

Ответ по критерию — не перечисление регионов, а **граница неизменяемого ядра и настраиваемой
переменной части** (раздел 1–2) + **реалистичный порядок** (раздел 4) + **конкретные условия
адаптации** (раздел 5) + **риски** (раздел 6). Ядро не зависит от гео-сущностей: справочник
локаций нормализуется по ФИАС, события приходят фидом, документы — из шаблона.

## 8. Метрики успеха тиражирования

- Доля выездов, оформленных через сервис (цель: ≥ 80% в пилотной школе).
- Время сбора группы (цель: ≤ 24 ч).
- Число потерянных согласий (цель: 0).
- Утилизация «Пушкинской карты» школьниками (рост к базовой линии).
- Время учителя на организацию выезда (цель: ≤ 20 мин).
