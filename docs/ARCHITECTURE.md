## 1. Принцип: ports & adapters

Домен не знает про MAX. MAX — один из каналов доставки (адаптер). Это позволяет
подключить другой мессенджер/канал без изменения бизнес-логики (см. [`SCALING.md`](SCALING.md)).

```
        ┌──────────────────────── MAX (канал) ────────────────────────┐
        │  чат-бот (long polling / webhook)   │  мини-приложение (Webview) │
        └───────────────┬─────────────────────┴──────────────┬──────────┘
                        │ REST/JSON                           │ REST/JSON (nginx-прокси)
                        ▼                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                         CORE BACKEND (FastAPI)                            │
│                                                                           │
│  main.py        — REST API ядра (/api/v1/*), webhook, lifespan            │
│  bot.py         — MAX Bot Adapter: обработка Update, сценарии, напоминания│
│  services.py    — статусы, ответ родителя, билеты, контекст          │
│  documents.py   — генерация приказа (DOCX/PDF)                            │
│  max_client.py  — клиент MAX Bot API (httpx), команды, клавиатуры         │
│  max_validate.py— проверка подписи initData (HMAC-SHA256)                 │
│  models.py      — доменная модель (SQLModel)                              │
│  catalog_seed.py— модельные данные каталога (явно помечены)               │
│  config.py      — настройки из окружения (секреты только тут)             │
│                                                                           │
│                         SQLite (SQLModel/SQLAlchemy)                      │
└──────────────────────────────────────────────────────────────────────────┘
```

## 2. Компоненты и ответственность

| Компонент | Файлы | Ответственность |
|---|---|---|
| REST API ядра | [`main.py`](../backend/app/main.py) | приём запросов, валидация, транзакции, отдача документов |
| MAX Bot Adapter | [`bot.py`](../backend/app/bot.py) | Update → действия; приветствие, кнопки согласия, `/trips`, напоминания |
| Домен | [`services.py`](../backend/app/services.py) | правила «Сводки ответов», идемпотентность согласий, контекст родителя |
| Документы | [`documents.py`](../backend/app/documents.py) | приказ + 3 приложения, DOCX (python-docx) и PDF (reportlab) |
| Клиент MAX | [`max_client.py`](../backend/app/max_client.py) | HTTP-контракт MAX, не роняет сервис при сбоях сети |
| Валидация MAX | [`max_validate.py`](../backend/app/max_validate.py) | подпись initData, свежесть auth_date |
| Модель данных | [`models.py`](../backend/app/models.py) | классы, ученики, родители, выезды, участники, аудит |
| Мини-приложение | [`miniapp/src/`](../miniapp/src) | каталог, «Сводка ответов», экран родителя, MAX Bridge |

## 3. Поток данных (основной сценарий)

```
Родитель нажимает кнопку в MAX
   → MAX присылает Update (message_callback)
   → BotService.handle_update → services.apply_consent (транзакция в БД)
   → запись в ConsentAudit (кто, когда, источник)
   → bot.answer_callback (подтверждение)
   → mini-app на следующем открытии видит новый статус («Сводка ответов»)
```

Учительские действия (каталог, создание выезда, документы) идут напрямую через REST из mini-app.

## 4. Ключевые технические решения и их обоснование

| Решение | Обоснование |
|---|---|
| **SQLite** вместо PostgreSQL | ноль настройки, воспроизводимость в Docker, достаточная нагрузка для MVP |
| **Модульный монолит** вместо микросервисов | быстрее собрать и надёжнее запустить (см. рекомендации архитектурного референса) |
| **Long polling + webhook** | polling для демо/dev, webhook — прод-канал (по документации MAX) |
| **httpx-клиент не бросает исключений** | падение внешнего шлюза не роняет сервис (критерий стабильности) |
| **Идемпотентные согласия** | повторное действие не перезаписывает статус (правило «двух родителей») |
| **Журнал ответов отдельной таблицей** | кто ответил, когда, телефон, канал |
| **Модельные данные помечены** | честность: `source` у событий, `dataset.is_mock` в `/api/v1/meta` |
| **Секреты только из окружения** | токен не в коде; проверяется тестом SEC-1 |

## 5. Обработка ошибок и стабильность

- Валидация входных данных (Pydantic) → 422 с понятным сообщением.
- Отсутствующие сущности → 404 с `detail`, без стектрейсов.
- Сетевые сбои MAX → логируются, метод возвращает `None`, сервис жив (тест BOT-15).
- Бот глотает исключение в одном Update, не останавливая обработку остальных (BOT-11).
- Повторный прогон сценария стабилен (NFR-3, adversarial CRIT-5 на параллелизм).

## 6. Тестируемость как архитектурное свойство

- Домен отделён от транспорта → тестируется без сети (pytest, 147 тестов).
- Адаптер MAX тестируется через эмулятор протокола (`scripts/e2e_agent.py`).
- UI тестируется через подмену библиотеки MAX Bridge (Playwright, `ui-e2e/`).
- Полный прогон одной командой: `./scripts/run_all_tests.sh`.

## 7. Ограничения MVP (осознанные)

- Нет ролей/аутентификации API в демо (в проде включается проверка initData — реализована).
- Каталог — снапшот (реальный API требует доступа).
- SQLite не для горизонтального масштабирования (в проде — PostgreSQL).
