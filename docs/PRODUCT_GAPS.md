# Продуктовые пробелы «ClassGo»: честный разбор флоу двух ролей и недостающие фичи

Документ для защиты. Не комплиментарный: фиксирует, где флоу реально работают, где обрываются,
каких фич не хватает по PRD (`docs/input/Продуктовое_описание.md`, UC-1..UC-7) и по реальной боли
учителя и родителя. Каждая находка оценена по влиянию на критерии жюри и приоритету.

Метрика, которую максимизируем, — оценка жюри: продуктовая 40% (масштабирование 35%, ценность 25%,
UX/UI 20%, целостность 15%, презентация 5%) + техническая 60% (работоспособность 30%, интеграция 20%,
архитектура 20%, стабильность 10%, безопасность 10%, документация 10%). Правило: опциональная фича,
дающая баллы, — обязательна.

## 1. Как есть: флоу учителя (классного руководителя)

Первый контакт — бот `@t158_hakaton_max_bot`, затем мини-приложение. Ниже по шагам, с пометкой
`[реализовано]` / `[частично]` / `[отсутствует]`.

1. **[частично] UC-1 — заведение класса.** Бэкенд умеет `POST /api/v1/classes/import` (CSV/XLSX,
   парсинг ФИО, даты рождения `ДД.ММ.ГГГГ`/`ГГГГ-ММ-ДД`, телефонов родителей), есть валидация и
   `skipped_rows`. **Но в UI мини-аппа нет экрана импорта** — учитель не может загрузить файл класса
   из интерфейса. В демо работает только сидированный класс 8-Б (24 ученика, [`catalog_seed.py`](../backend/app/catalog_seed.py)).
   Реальный учитель физически не заводит свой класс через интерфейс.
2. **[реализовано] UC-2 — подбор события.** Каталог [`CatalogScreen.tsx`](../miniapp/src/screens/CatalogScreen.tsx)
   с фильтрами: возраст (0+/6+/12+/16+), «Пушкинская карта», «Бесплатные», поиск по названию.
   Город захардкожен (`city: "Казань"`). Отсутствуют фильтр по дате/периоду (заявлен в PRD) и
   сортировка/пагинация.
3. **[частично] UC-3 — публикация выезда в чат.** Создание выезда из UI работает
   (`Создать выезд` → участники создаются по всем ученикам). **Кнопки «Опубликовать в чат класса» в
   UI нет** — эндпоинт `POST /api/v1/excursions/{id}/publish?chat_id=...` и текст карточки
   ([`bot.py`](../backend/app/bot.py) `publish_to_chat`) реализованы, но из интерфейса не вызываются.
   Назначение второго сопровождающего (UC-3 п.2) отсутствует — есть только один
   `responsible_teacher` из класса.
4. **[реализовано] UC-6 — «Сводка ответов».** Дашборд [`DashboardScreen.tsx`](../miniapp/src/screens/DashboardScreen.tsx)
   со сводкой GREEN/YELLOW/GREY/RED, прогресс-баром, рассадкой «ряды мест», построчным списком.
   Кнопка «Напомнить не ответившим» шлёт точечные пуши по GREY/YELLOW ([`services.py`](../backend/app/services.py)
   `remind_targets` + `reminder_text`). **Повторных/автоматических напоминаний нет** — только ручной
   дожим по кнопке.
5. **[частично] UC-7 — пакет документов.** `export-order` генерирует DOCX+PDF: приказ + 3 приложения
   (список участников, реестр согласий ПЭП, лист инструктажа) — [`documents.py`](../backend/app/documents.py).
   **Нет маршрутного листа и уведомления в ГИБДД** (ПП РФ №1527, обязательны при автобусной перевозке),
   нет согласия на обработку ПДн (152-ФЗ), нет списка для покупки билетов. **Кнопки «Обновить приказ»
   (корректирующий список при ЧП, PRD §5.3) нет** — есть только повторная генерация с инкрементом версии.

**Итог по учителю:** сквозной путь «каталог → создать → дашборд → напомнить → приказ» работает в демо,
но два ключевых шага PRD (импорт класса и публикация в чат) живут только на уровне REST и недостижимы
из интерфейса — основной сценарий для жюри обрывается на полпути.

## 2. Как есть: флоу родителя (законного представителя)

1. **[частично] Вход и идентификация.** Родитель попадает в мини-апп из бота по
   `?startapp=<student_id>` или по MAX-профилю через `/api/v1/parent/context` (после привязки к боту
   через одноразовый диплинк `bind_<code>`). **Bug:** [`App.tsx`](../miniapp/src/App.tsx) берёт только
   `children[0]` — родитель с несколькими детьми видит только первого ребёнка.
2. **[реализовано] UC-4 — согласие.** [`ParentScreen.tsx`](../miniapp/src/screens/ParentScreen.tsx):
   «Отпускаю ребёнка» / «Не сможет поехать» (причина), идемпотентность, правило «двух родителей»
   (первый подписавший блокирует статус, [`services.py`](../backend/app/services.py) `apply_consent`).
   **Ограничение:** импорт создаёт одного родителя на ученика, привязка берёт первого
   `ParentContact` (`.first()`), т.е. сценарий «мать и отец в одном чате» смоделирован, но не
   реализован на данных. Юридически ПЭП фиксирует `signed_at`/`signed_by_name`/`signed_by_phone`,
   но **не сохраняет подтверждающий признак (hash initData / max_user_id)** — см. §4, риск ПЭП.
3. **[реализовано, с нюансом] UC-5 — билет.** «Купить билет на сайте музея» (`openLink` на
   `ticket_sale_url`) + чекбокс «Билет куплен». **Нет поля для номера билета в UI** (бэкенд его
   принимает, UI не шлёт). Нет подсказки, что «Пушкинская карта» индивидуальна и для класса покупается
   каждым родителем отдельно (групповой покупки по ПК нет).
4. **[реализовано] Напоминания.** Родитель привязанный к боту получает пуш с кнопками согласия.
   Автоматических напоминаний о дедлайне нет.

**Итог по родителю:** базовый сценарий «открыл → подтвердил → отметил билет» работает. Слабое место —
идентификация и multi-child, а также юридическая весомость согласия (нет ни согласия на ПДн, ни
подтверждающего признака подписи).

## 4. Критические допущения и риски (для честности перед жюри)

- **ПЭП без криптографии.** По 63-ФЗ простая электронная подпись — это «коды, пароли и иные средства»,
  подтверждающие отправителя; для признания документа равнозначным бумажному нужны либо НПА, либо
  соглашение сторон. Кнопка «Отпускаю» в мессенджере фиксирует факт и время, но **не является
  квалифицированной подписью**. Для пилота это решается локальным актом школы («согласие в цифровой
  форме через MAX признаётся равнозначным»). Надо честно назвать это допущением, а не выдавать за
  полноценную ПЭП. Источник: 63-ФЗ ст. 5–6 — https://www.consultant.ru/document/cons_doc_LAW_112701/
- **Пушкинская карта индивидуальна.** Групповой покупки по ПК нет: каждый владелец 14–22 лет покупает
  билет сам. Для класса это значит «24 отдельных покупки», а для начальной школы ПК недоступна вовсе.
  Сервис не должен обещать «класс покупает по ПК разом». Источники: https://culture.gosuslugi.ru/,
  https://www.culture.ru/pushkinskaya-karta
- **PRO.Культура.РФ.** API реален (JSON, для инфопартнёров), но в демо каталог — модельный снапшот
  (честно помечен `source` и `dataset.is_mock`). Реальная интеграция — следующий шаг.
  Источники: https://pro.culture.ru/documentation/proAPI.pdf , https://opendata.mkrf.ru/
- **Анти-поборы.** Сбор денег учителем/школой незаконен (ст. 43 Конституции, ст. 5/8 273-ФЗ); сервис
  верно не касается денег — оплата напрямую в кассу. Источники: https://rskrf.ru/consumer_rights/solutions/services/zakonny-li-pobory-v-shkole/ ,
  https://amulex.ru/daily/obrazovanie/pobory-v-shkolah-ne21fb0v/

## 5. Топ рекомендаций к реализации до защиты

Порядок = приоритет по влиянию на баллы при минимальной трудоёмкости.

1. **P0, дешёво и максимально заметно:** доделать сквозной сценарий до конца — кнопка «Опубликовать
   в чат» (№1) и экран импорта класса (№2). Без них «основной сценарий от начала до результата» не
   проходится целиком, а это 30% технической оценки + пункт допуска.
2. **P0, баги реального использования:** мультидети (№3) и два родителя (№4) — это не «фичи», а
   исправление ломающих сценарий ограничений; жюри проверяет устойчивость к повторному проходу.
3. **P1, юридическая полнота пакета документов:** маршрутный лист + уведомление ГИБДД (№5) и согласие
   на ПДн (№6) — превращают «приказ» в реальный пакет, это бьёт в целостность (О) и подтверждает
   главную боль учителя (отчётность/безопасность), а также усиливает вектор масштабирования
   «генератор нормативных документов».
4. **P1, корректность сценария билета:** предупреждение про Пушкинскую карту и возраст (№7), поле
   номера билета (№9), кнопка «Обновить приказ» (№8).
5. **P1, честность ПЭП:** добавить признак подписи в аудит (№10) и зафиксировать в материалах
   допущение о равнозначности через локальный акт школы.
6. **P2, масштабирование (самый весомый критерий 35%):** хотя бы в тексте презентации раскрыть роль
   администрации (№11) и аналитику департамента (№13) — без кода это закрывает критерий «потенциал
   масштабирования» на словах; с кодом — выигрывает финал.

## 6. Микрo-UX и «полезные мелочи»

Второй заход ресерча: пласт мелких удобств, которые не закрывают «сквозной сценарий» (§1–§5),
но набирают баллы на критериях **UX/UI (20% прод.)** и **ценность (25%)** при минимальной
трудоёмкости — то, что жюри видит и может «пощупать» за 5 минут. Ниже каталог мелочей по ролям
и этапам, с честной пометкой **«есть»** (уже реализовано, где в коде) / **стоит делать** (P0/P1) /
**не делать** (P2 — избыточно для хакатона, слабый балл за работу).

Сокращения и шкалы те же, что в §3: критерии **М/Ц/UX/О/Р/И/Б**; трудоёмкость **S/M/L**;
приоритет **P0/P1/P2**. Для каждой мелочи — «есть/нет/стоит ли».

### 6.1 Каталог: подбор и сравнение событий

Бэкенд [`main.py`](../backend/app/main.py) `list_culture_events` принимает только `city/age/pushkin/free`;
клиентский поиск по `title+venue` есть в [`CatalogScreen.tsx`](../miniapp/src/screens/CatalogScreen.tsx:58).
Модель [`CultureEvent`](../backend/app/models.py:89) уже хранит `event_date`, `duration_min`, `price`,
`address` — поэтому дата/длительность/цена/сортировка реализуемы на существующих данных без миграций.

| Фича | Зачем (боль / критерий) | Что даёт жюри | Трудоёмкость | Приоритет | Источники |
|---|---|---|---|---|---|

### Топ-10 мелочей: максимум баллов за минимум работы

1. **Сортировка каталога** (по дате/цене/длительности) — `S`, параметр + `order_by`.
2. **Фильтр по дате/периоду + «ближайшие/на этих выходных»** — `S`, закрывает заявленный PRD UC-2.
3. **Авто-фильтр «подходит моему классу по возрасту»** — `M`, уникальный отличитель от любой афиши, бьёт в целостность.
4. **Дедлайн-таймер / обратный отсчёт** — `S`, срочность и прозрачность в дашборде.
5. **Экран прозрачности ПДн/ПЭП** — `S`, бьёт в безопасность (10% тех.) и доверие администрации.
6. **Экспорт CSV списка участников** — `S`, практическая мелочь для туроператора/кассы.
7. **ICS «добавить в календарь» родителю** — `S`, стандарт билетных сервисов, снижает «забыли».
8. **«Что взять с собой» + чек-лист выезда** — `S/M`, закрывает «день выезда» циклом.
9. **Дубликат выезда / «повторить прошлый»** — `S`, вектор тиражируемости.
10. **Поиск ученика + фильтр строк по статусу** — `S`, разгружает список класса.

Все десять — «S-мелочи», которые жюри видит и может проверить за минуту; они не конкурируют с
P0-фиксами сквозного сценария (§5), а дополняют их там, где балл дешёвый.
